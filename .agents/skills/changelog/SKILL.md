# 更新日志撰写规范 (Changelog Skill)

本规范用于指导查分器项目更新日志（`public/docs/changelog.md`）的撰写、追加与审查。更新日志统一发布本系统（包含当前前端仓库与同级 Go 后端服务仓库）面向外部的所有改动，确保为最终用户（玩家）和第三方开发者提供准确、连贯、高价值的发布记录。

---

## 一、条目判定标准：写什么与不写什么

### 1. 核心判定原则：外部可观测性与决策价值

更新日志的核心受众是**最终用户（玩家）**与**第三方 API 开发者**。判定一条改动是否记录的唯一基准是：**该改动是否在系统黑盒边界之外产生了可被观测到的行为变化，或者是否影响了外部使用者的决策与交互**。

```
[待判定的提交 / PR / 变更集合]
          │
          ▼
该变更是否对最终用户或第三方开发者产生可感知的黑盒行为变化？
(如：新增界面/能力、交互流程变动、开放 API / 结构体变更、报错响应变化、体感性能优化、已暴露缺陷修复)
          ├─ 否 ──► 【坚决不写】（内部工程细节，直接过滤）
          └─ 是
                │
                ▼
该修复/改动是否属于针对「本期尚未发布代码」的修复或反复打磨？
          ├─ 是 ──► 【合并入原条目】（修改/折叠进原始条目，不单独记一条修复）
          └─ 否 ──► 【写入更新日志】（提炼为面向外部的规范条目）
```

### 2. 机械排除清单（绝对不写）

以下类别的变更属于内部开发与维护细节，**严禁**写入更新日志：

1. **纯内部代码重构（Refactor）**：函数提取、内部类型重命名、代码位置移动、内部状态机改写，只要对外输入输出与黑盒行为完全一致。
2. **无外部感知的性能微调（Invisible Perf）**：内部内存分配优化、基准测试（Benchmark）调优、微秒级执行优化，未带来页面渲染或接口加载等肉眼可见的体感改善。
3. **注释与内部工程文档（Docs & Comments）**：JSDoc 注释整理、代码说明、开发环境指引（非 `public/docs/` 面向用户的公开文档变更）。
4. **CI/CD、工程脚本与静态检查（Tooling & CI）**：GitHub Actions 工作流微调、ESLint/Prettier 格式化、tsconfig 编译配置、打包参数微调。
5. **常规依赖包版本升级（Dependency Bumps）**：常规的包版本号更新（如 Sentry、构建插件升级），且并未向最终用户提供新特性或解决已知外部缺陷。
6. **自动化测试与基准套件（Tests & Benchmarks）**：单元测试、端到端测试用例、回归防护测试、基准测量脚本的增删改。
7. **内部运维与部署支持（DevOps & Internal Observability）**：Docker 配置调整、优雅停机信号处理、非生产环境定时监控忽略等内部运行时细节。
8. **未开放的隐藏半成品（Stubs & Dark Launches）**：尚未向普通用户或第三方暴露入口、处于禁用或隐藏状态的占位实验性代码。
9. **回滚配对变动（Reverts）**：发版周期内先提交后被完全回滚的代码互相抵消，不产生任何日志。

### 3. 必须记录清单（必须写）

1. **新功能与新界面特性（Features & UI）**：新增页面、新增查询/筛选模式、新增个人设置项、新增交互动作（如快捷键、手势）。
2. **交互行为与业务规则变更（Behavior Changes）**：排序与过滤算法调整、账号安全策略演变（如支持邮箱验证、通行密钥登录）、数据同步规则变化。
3. **已发布缺陷修复（User-facing Bugfixes）**：针对历史已发布版本中用户曾遇到过的界面崩溃、排版溢出、数据计算偏差、爬取中断等问题的修复。
4. **外部 API 与认证协议变更（API & Protocols）**：新增开放 API 接口、数据结构体增删字段、OAuth 2.0 / OpenID Connect 协议支持、状态码与错误信息格式变化。
5. **破坏性变动（Breaking Changes）**：删除既有接口、废弃或删除结构体字段、增加破坏向后兼容的必填项。
6. **体感级性能与体验优化（Perceptible Perf & UX）**：具有明显感官差异的加载速度提升、长列表滚动流畅度改善、关键动画优化。

## 二、条目密度与主动合并准则（控制密度与消除噪音）

### 1. 实测校准锚点与密度基准

- **历史数据校准锚点**：本文件历史上每个日期小节的条目数**中位数是 2 条**，历史最大仅 6 条（如 2026/6/24）。实测曾按旧规范初筛产出 16 条（2026/9/7），达历史次高值的近 3 倍。这证明仅靠「机械排除不该写的」远远不够，必须**主动向上合并**。
- **条目密度参考**：单个日期小节通常为 **2~6 条**。**密度是校准参考，不是硬性上限**。
- **超标复查判据（非硬性上限）**：若初筛后单日条目**超过 6 条**，仅作为「粒度可能过细」的校准参考信号，提示回头检查是否有可合并项，而非必须削到 6 条以内的硬指标。若按「同一功能区域 / 同一问题面」正确归并后仍略超 6 条，**应当保持拆分，超出完全可接受**，严禁为压进 6 条以内而强行合并无关改动。
- **核心价值判据**：读者关心的是**“这次更新我能感觉到什么变化”**，而不是**“你们改了几个地方”**。

### 2. 合并的前提条件与反面禁令（严禁凑数合并）

- **合并的前提条件**：只有属于**同一功能区域**（如首页、谱面预览、同步数据、开发者面板）或**同一用户可感知问题面**的改动才可以合并。**「都是修复」「都是本次更新」绝不是合并理由**。
- **严禁凑数合并**：不得为了把条目数压进 2~6 条而把无关改动并入同一条。严禁使用「并」「以及」把两件无关事情生硬缝进一句话。
  - ❌ `开放 API 支持 Accept-Encoding 内容压缩，以及更新开发者页面交流群链接`（接口能力与社区外链毫无关联）
  - ❌ `修复部分旧版本 iOS/Safari 页面无法使用，并修复登录会话过期后未弹出提示的问题`（两处独立故障仅因“同为修复”被强行缝合，必须保持拆分）

### 3. 主动合并方向与策略

1. **功能区域收敛**：把同一功能区域（如首页、成绩管理、谱面预览、同步数据）的多处分散改动归并为一条概括性描述，或归并为「一条父条目 + 2~3 项精炼子条目」。
2. **问题面统一概括**：多个分散的修复若指向同一个用户可感知的问题面（如跨设备显示异常、某流程偶发失败），直接合并为一条概括性描述，切忌按提交或底层模块逐个罗列。
3. **未发布修复合并（过程去噪）**：若某项修复是针对当前批次「尚未正式发布的代码」所做的修补或打磨，**严禁**单列为修复条目，必须完全消化、折叠进该功能的原始条目中。只有历史已发布版本中真实存在过的缺陷，才可作为独立修复记录。
4. **多步提交提炼**：同一特性经历的多轮提交（功能开发、样式调整、补丁修复），对外统一提炼为一条最终发版成果。

## 三、读者分层与用词规范

### 1. 读者分层与用词准则（核心分水岭）

必须严格区分两类条目，读者不同，用词边界截然不同：

```
                              [待转译条目]
                                    │
                  该改动是否需要第三方开发者改代码才能适配？
                                    │
                    ┌───────────────┴───────────────┐
                   否                               是
                    ▼                               ▼
              【玩家向条目】               【第三方开发者向条目】
        面向普通用户，描述感知变化          面向 API 开发者，精准契约声明
        坚决禁止出现底层实现技术词汇        必须使用精确字段、结构体、接口路径
```

- **分层判据**：改动**是否需要第三方开发者改代码才能适配**。
- **类别 1：玩家向条目（绝大多数界面、功能与常规修复）**
  - **原则**：用普通用户能理解的话描述直观可感知的变化。普通玩家不知道也不关心底层技术实现。
  - **禁用词反面清单（严禁泄漏以下实现术语）**：
    `水合`、`hydration`、`离屏合成`、`响应式断点`、`探针`、`派生数据`、`序列化`、`并发请求`、`内部错误`、`解析异常`、`SSE`、`长连接`，以及`浮标`、`实时状态连接`等内部实现描述。（注：`Brotli`、`Gzip`、`Accept-Encoding` 等网络传输词汇仅限 API 条目，严禁混入普通玩家条目）。
  - **改写示范**：
    - ❌ `修复在低版本 Safari 与 iOS 设备上页面水合失败导致无法交互、移动端响应式排版错乱以及文档代码块报错的问题`
    - ✔ `修复部分旧版本 iOS 与 Safari 上页面无法正常使用的问题`
    - ❌ `首页右下角新增构建版本信息浮标，展示当前版本与代码提交记录，并随页面滚动自动显隐`
    - ✔ `首页右下角新增版本信息展示`
    - ❌ `优化打击效果与音符渲染性能，大幅缩减离屏合成开销并改善动画流畅度`
    - ✔ `优化谱面预览的渲染性能，提升动画流畅度`
    - ❌ `修复同步数据时若玩家个人主页解析异常，可能导致服务内部错误的问题`
    - ✔ `修复特定情况下同步个人数据可能失败的问题`
- **类别 2：第三方开发者向条目（API 变更）**
  - **原则**：读者就是开发者，**可以且应当使用精确的接口术语** —— 字段名、结构体名、接口路径、协议名。精准传达系统契约变化。
  - **不受玩家反面清单限制**：允许且必须精确使用如 `Player` / `Score` 结构体、`play_time`、`last_played_time`、OAuth 2.0、OpenID Connect、`client_id`、`Accept-Encoding`（Brotli / Gzip 压缩协商）等接口与协议术语。
  - **典型示例**：`- Score 结构体中新增 last_played_time 字段，用于获取谱面的最后游玩时间`

### 2. 视角要求

- **外部黑盒观察者视角**：描述“系统现在呈现什么表现”或“调用方能够获得什么”，而非“开发者在代码里做了什么”。
- **禁止出现内部开发细节**：严禁出现内部模块名/文件名、数据库表名、内部函数名、内部状态变量、commit hash 或内部 PR 标题原文。

### 3. 用词习惯与句式规范（严格遵循历史风格）

- **「现在」的规范用法**：
  历史日志高频使用「现在」来表达行为切换、默认值调整或新能力赋予。
  - `[主体] 现在支持 / 现在可以 / 现在会 / 现在返回 ...`
  - 典型范式：`OAuth 应用现在最多可以登记 10 个回调地址`、`账号现在支持验证邮箱`、`曲目搜索现在会高亮匹配的内容`。
- **起始动词与句式约定**：
  - **`新增`**：用于全新页面、全新功能、全新接口或字段（例：`新增通知中心`、`开发者面板新增 API 用量统计`）。
  - **`修复`**：**行末必须以「...的问题」结尾**，且必须讲清触发场景与直观错误现象（例：`修复曲目难度在历史版本中不存在时，历史定数显示异常的问题`、`修复少部分情况下，用户操作可能会提示失败的问题`）。
  - **`优化`**：用于性能、视觉、易用性改善（例：`优化了成绩排行榜的加载速度`、`优化表单中用户名、邮箱等输入框的错误提示`）。
  - **`支持`**：用于支持新输入格式、新协议或操作方式（例：`现在支持手动上传 HTML 同步游戏数据`、`支持将成绩导出为 .csv 文件`）。
  - **`重新设计`**：用于页面架构重构与适配升级（例：`重新设计成绩管理页面，更好地适配桌面端与移动端：`）。
  - **`移除 / 删除`**：用于移除不再适用的限制或过时功能（例：`移除了曲目搜索和收藏品搜索的最大搜索结果限制`）。
- **行内标记与链接格式**：
  - **标识符代码块**：字段名、参数名、状态码、配置项用行内反引号包裹，如 `` `play_time` ``、`` `client_id` ``、`` `404` ``。
  - **站内链接**：涉及站内路由或帮助文档时，使用相对路径链接，如 `[站点设置](/user/settings)`、`[文档说明](/docs/api/...)`。
  - **Issue / PR 链接**：属于外部贡献或有公开 issue 跟踪的条目，在行尾使用**全角括号**附加链接，格式为 `（[#<编号>](<完整URL>)）`。常规内部提交无需添加。
- **敏感词与中立规范**：
  - 严禁出现具体游戏名称、反编译工具名称或私有数据来源。一律使用通用技术与业务名词（如“查分器”、“曲目”、“谱面”、“成绩管理”、“收藏品”、“开放接口”）进行表述。

## 四、前后端统一更新日志处理规范

### 1. 统一发布载体

- 本项目的更新日志维护在前端仓库的 `public/docs/changelog.md` 中。
- 同级 Go 后端服务仓库没有独立的更新日志，**后端所有面向外部的改动均直接汇总写入本文件**。

### 2. 避免前后端割裂

- **严禁打标签**：同一日期下的条目**严禁**标记 `[前端]`、`[后端]`、`[API]`，也不得设立前后端专属小标题。
- **按业务功能整合**：若同一特性涉及前后端协同改动（例如后端新增回调限制并在前端开发者页面提供表单配置），合并归纳为以用户/开发者为中心的完整描述。

### 3. 后端/API 变动的人类语言转译指南

后端 Conventional Commits 需按以下模式转译为清晰的契约声明与业务效果：

1. **数据同步与业务逻辑改动**：
   - 提交：`fix(score): ignore a client-supplied play_time`
   - 日志：`- 上传成绩时不再接受客户端提供的游玩时间（`play_time`），该字段仅通过 NET 的 HTML 上传写入`
2. **API 结构体字段增删**：
   - 提交：`feat(scores): add last_played_time to Score`
   - 日志：`- Score 结构体中新增 `last_played_time` 字段，用于获取谱面的最后游玩时间`
3. **协议与安全特性**：
   - 提交：`feat(oauth): cap dynamic client registrations to 10`
   - 日志：`- OAuth 应用现在最多可以登记 10 个回调地址`
   - 提交：`feat(auth): support openid connect identity tokens`
   - 日志：`- 新增 OpenID Connect 支持，可通过 openid、profile 和 email 权限完成用户登录与身份识别`
4. **错误码与响应格式**：
   - 提交：`fix(oauth): answer an unknown client_id with 404, not 500`
   - 日志：`- OAuth 授权时使用已失效的 client_id 现在返回 404，客户端可据此重新注册`

### 4. 破坏性变动处理（Breaking Changes）

当改动破坏了既有契约（如删除 API 接口、移除结构体字段、修改必填参数）时，必须在当日普通条目下方建立专属三级小节：

```markdown
### ⚠ 破坏性变动

以下变动将会影响开发者，请检查你的代码是否受到影响：

- [结构体名] 结构体中删除字段：`旧字段名`
  > [替代接口名](/docs/api/...)请使用 `新字段名` 替代
- 删除部分过时接口：
  - 接口名称：`/api/v0/old_path`
    > 请使用 `/api/v0/new_path` 代替
```

## 五、排版结构与 Git 操作规范

### 1. 文档全局排版结构

- 文件顶部固定格式：

  ```markdown
  # 更新日志

  ---

  ## YYYY/M/D
  ```

- **日期标题规范**：
  - 层级：二级标题 `## YYYY/M/D`。
  - **绝对禁止月份与日期前导补零**：必须使用 `2026/8/6`、`2026/6/1`，严禁写成 `2026/08/06` 或 `2026/06/01`。
  - 时间顺序：**倒序排列**，最新的发版日期始终插入在最上方（紧接在 `---` 之后）。
- **条目层级缩进**：
  - 独立条目：使用一级列表 `- `。
  - 复合特性条目：首行以冒号结尾，子条目使用 2 个空格缩进：
    ```markdown
    - 谱面预览：
      - 改进滑条的扇形渲染
      - 修复变速谱下进度条小节刻度与播放头不对齐的问题
    ```
- **容器与引用块**：
  - 用户配置提醒可使用 VitePress 容器：`::: info 提示\n...\n:::`。
  - 迁移补充指引可使用引用块：`> 提示文本`。

### 2. Git 操作与版本控制规则

- **文件跟踪状态**：
  - 文件路径为 `public/docs/changelog.md`，处于 git 正常追踪状态。
  - 提交流程中直接执行标准的 `git add public/docs/changelog.md` 即可，**不需要也不得使用 `git add -f`**。
- **澄清 .gitignore 规则**：
  - 仓库根目录 `.gitignore` 中的 `/docs/` 规则仅针对仓库根目录下的 `docs/` 目录，与 `public/docs/` 完全无关。更新日志文件未被 git 忽略。
- **审查安全限制**：
  - 查阅改动历史时，仅使用只读命令（如 `git log --oneline`、`git status`、`git diff`）。
  - 未获授权严禁执行重置工作区或修改 git 状态的破坏性命令。

## 六、从 Commit/PR 到更新日志的完整工作流程

```
步骤 1：查阅改动 ──► 检查前端仓库与同级 Go 后端仓库自上次发版以来的提交与合并 PR
        │
步骤 2：机械过滤 ──► 对照「排除清单」，剔除内部重构、CI、依赖升级、测试、无感知优化与回滚对消
        │
步骤 3：主动合并 ──► 按功能区域与问题面归并（参考单日 2~6 条，严禁无关凑数），未发布修复直接折叠进原条目
        │
步骤 4：读者分层 ──► 区分玩家向（通俗、禁用实现术语）与 API 向（精确契约术语），应用标准句式
        │
步骤 5：规范插入 ──► 在 public/docs/changelog.md 顶部按 ## YYYY/M/D 格式排版插入
```

## 七、新增条目完整最小示例

以下展示一个包含独立功能、复合子列表、API 变更、Bug 修复及破坏性变动的标准完整更新日志片段（条目数通常在 2~6 条）：

```markdown
## 2026/9/7

- 账号现在支持绑定第二邮箱，用于接收安全提醒
- 谱面预览：
  - 优化滑条动画帧率，减少低配设备上的卡顿（[#102](https://github.com/Lxns-Network/maimai-prober-frontend/pull/102)）
  - 修复变速谱面中小节线在特定分辨率下错位的问题
- 成绩管理页面新增批量导出功能，支持导出为 CSV 格式
- `Player` 结构体中新增 `verified_email` 字段，用于获取用户邮箱验证状态
- OAuth 授权时使用未授权的回调地址现在返回 404，并提示详细原因
- 修复在弱网环境下同步数据时，同步进度条可能会卡在 99% 的问题

### ⚠ 破坏性变动

以下变动将会影响开发者，请检查你的代码是否受到影响：

- `Score` 结构体中删除字段：`legacy_token`
  > 请改用请求头携带的个人 API 密钥进行身份认证
```
