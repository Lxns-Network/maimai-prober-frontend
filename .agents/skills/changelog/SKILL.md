# 更新日志撰写规范 (Changelog Skill)

指导查分器项目更新日志（`public/docs/changelog.md`）的撰写与审查。统一发布前端与同级 Go 后端面向外部的所有改动，服务最终用户（玩家）和第三方开发者。

---

## 一、条目判定标准：写什么与不写什么

### 1. 核心判定原则：外部可观测性与决策价值

更新日志的核心受众是**最终用户（玩家）**与**第三方 API 开发者**。判定改动是否记录的基准是：**该改动是否在系统黑盒边界之外产生了可被观测的行为变化，或影响了外部使用者的决策与交互**。

```
[待判定的提交 / PR / 变更集合]
          │ 是否产生外部可感知的黑盒行为变化？
          ├─ 否 ──► 【不写】（内部工程细节，直接过滤）
          └─ 是
                │ 是否属于针对「本期未发布代码」的修复或反复打磨？
                ├─ 是 ──► 【合并入原条目】（折叠进原始条目，不单列修复）
                └─ 否 ──► 【写入更新日志】（提炼为面向外部的规范条目）
```

### 2. 机械排除清单（绝对不写）

以下属于内部开发与维护细节，严禁写入更新日志：

1. **纯内部代码重构（Refactor）**：函数提取、类型重命名、内部状态机改写，对外行为完全一致。
2. **无外部感知的性能微调（Invisible Perf）**：内存分配优化、微秒级执行优化，未带来肉眼可见的体感改善。
3. **注释与内部工程文档（Docs & Comments）**：JSDoc 整理、代码说明、开发环境指引（非 `public/docs/` 公开文档）。
4. **CI/CD、工程脚本与静态检查（Tooling & CI）**：GitHub Actions 工作流、格式化配置、tsconfig 编译与打包微调。
5. **常规依赖包版本升级（Dependency Bumps）**：未向最终用户提供新特性或解决已知外部缺陷的常规包升级。
6. **自动化测试与基准套件（Tests & Benchmarks）**：单元测试、端到端用例、回归防护与基准测试脚本。
7. **内部运维与部署支持（DevOps & Internal Observability）**：Docker 配置、优雅停机、非生产环境监控等运行时细节。
8. **未开放的隐藏半成品（Stubs & Dark Launches）**：未暴露入口、处于禁用或隐藏状态的占位实验性代码。
9. **回滚配对变动（Reverts）**：同一未发布窗口内引入又被完全回滚的改动互相抵消，不产生任何日志。

### 3. 必须记录清单（必须写）

1. **新功能与新界面特性**：新增页面、查询/筛选模式、个人设置项、交互手势/快捷操作。
2. **交互行为与业务规则变更**：排序/过滤算法调整、账号安全策略演变、数据同步规则变化。
3. **已发布缺陷修复**：历史已发布版本中用户遇到过的界面崩溃、排版溢出、计算偏差等修复。
4. **外部 API 与认证协议变更**：新增开放接口、结构体增删字段、OAuth 2.0 / OIDC 支持、状态码与错误信息格式变化。
5. **破坏性变动**：删除既有接口、废弃或删除结构体字段、增加破坏向后兼容的必填项。
6. **体感级性能与体验优化**：感官差异明显的加载提速、长列表滚动流畅度改善、关键动画优化。

## 二、条目密度与主动合并准则（控制密度与消除噪音）

### 1. 实测校准锚点与密度基准

- **历史数据校准锚点**：历史上单日条目数**中位数是 2 条**，历史最大为 6 条。仅靠机械排除不该写的远远不够，必须**主动向上合并**。
- **条目密度参考**：单个日期小节通常为 **2~6 条**。**密度是校准参考，不是硬性上限**。
- **超标复查判据（非硬性上限）**：若初筛后单日**超过 6 条**，仅作为「粒度可能过细」的复查信号，提示回头检查是否有可合并项。若按功能区域或问题面正确归并后仍略超 6 条，**应当保持拆分，超出是完全可接受的**，严禁为压进 6 条以内而强行合并无关改动。
- **核心价值判据**：读者关心的是**“这次更新我能感觉到什么变化”**，而非**“你们改了几个地方”**。

### 2. 合并的前提条件与反面禁令（严禁凑数合并）

- **合并的前提条件**：只有属于**同一功能区域**（如首页、谱面预览、成绩管理）或**同一用户可感知问题面**的改动才可合并。**「都是修复」「都是本次更新」绝不构成合并理由**。
- **严禁凑数合并**：严禁为了压条目数而合并无关改动；严禁使用「并」「以及」把两件无关事情强行缝进一句话：
  - ❌ `开放 API 支持 Accept-Encoding 内容压缩，以及更新开发者页面交流群链接`
  - ❌ `修复部分旧版本 iOS/Safari 页面异常，并修复登录会话过期后未弹出提示的问题`

### 3. 主动合并方向与策略

1. **功能区域收敛**：同一功能区域的多处改动归并为一条概括描述，或归并为「一条父条目 + 2~3 项精炼子条目」。
2. **问题面统一概括**：指向同一用户感知问题面的分散修复，合并为一条概括描述，切忌按 commit 逐个罗列。
3. **未发布修复折叠（过程去噪）**：针对当前批次尚未发布代码所做的修复与打磨，**必须折叠并入原条目**，严禁新增「修复了刚才功能的 bug」；只有原改动已发布过才单独记一条修复。
4. **多步提交提炼**：同一特性经历的多轮提交（开发、样式调整、打磨），对外统一提炼为一条发版成果。

## 三、读者分层与用词规范

### 1. 读者分层与用词准则（核心分水岭）

```
                      [待转译条目]
                            │ 是否需要第三方开发者改代码才能适配？
              ┌─────────────┴─────────────┐
             否                           是
              ▼                           ▼
        【玩家向条目】             【开发者向 API 条目】
   面向普通用户，描述感知变化    面向 API 开发者，精准契约声明
   严禁出现底层实现技术词汇      必须使用精确字段、结构体与路径
```

- **分层判据**：**是否需要第三方开发者改代码才能适配**。
- **类别 1：玩家向条目（绝大多数界面、功能与常规修复）**
  - **原则**：用普通用户能理解的话描述感知变化，不关心底层技术实现。
  - **禁用词清单（严禁泄漏以下实现术语）**：`水合`、`hydration`、`离屏合成`、`响应式断点`、`探针`、`派生数据`、`序列化`、`并发请求`、`内部错误`、`解析异常`、`SSE`、`长连接`、`浮标`、`实时状态连接`。（注：`Brotli`、`Gzip`、`Accept-Encoding` 等网络传输词汇仅限 API 条目，严禁混入普通玩家条目）。
  - **改写示范**：
    - ❌ `优化打击效果渲染性能，缩减离屏合成开销并改善动画流畅度` ➔ ✔ `优化谱面预览的渲染性能，提升动画流畅度`
    - ❌ `修复同步数据时若个人主页解析异常导致服务内部错误的问题` ➔ ✔ `修复特定情况下同步个人数据可能失败的问题`
- **类别 2：第三方开发者向条目（API 变更）**
  - **原则**：读者是开发者，**可以且应当使用精确的接口术语**：字段名、结构体名、接口路径、协议名（如 `Player` / `Score` 结构体、`play_time`、`last_played_time`、OAuth 2.0、OpenID Connect、`client_id`、`Accept-Encoding` 等）。
  - **示例**：`- Score 结构体中新增 last_played_time 字段，用于获取谱面的最后游玩时间`

### 2. 视角要求与句式规范

- **外部黑盒视角**：描述“系统呈现什么表现”或“调用方能获得什么”，而非“代码里做了什么”。严禁出现内部模块/文件名、数据库表名、函数名、commit hash 或内部 PR 标题。
- **「现在」的规范用法**：表达行为切换或新能力赋予，句式为 `[主体] 现在支持 / 现在可以 / 现在会 / 现在返回 ...`（例：`OAuth 应用现在最多可以登记 10 个回调地址`）。
- **起始动词与句式约定**：
  - **`新增`**：全新页面、功能或字段（例：`新增通知中心`）。
  - **`修复`**：**行末必须以「...的问题」结尾**，讲清场景与直观现象（例：`修复特定情况下同步个人数据可能失败的问题`）。
  - **`优化`** / **`支持`** / **`重新设计`** / **`移除`**：分别用于体验提升（`优化成绩排行榜加载速度`）、新格式协议（`支持导出为 .csv 文件`）、重构适配（`重新设计成绩管理页面`）与移除限制（`移除搜索结果数量限制`）。
- **行内标记与链接格式**：标识符、参数名、状态码用行内反引号（如 `` `play_time` ``、`` `404` ``）；站内链接用相对路径（如 `[设置](/user/settings)`）；外部贡献或公开 issue 在行尾用全角括号注明：`（[#<编号>](<完整URL>)）`。
- **敏感词与中立规范**：严禁出现具体游戏名称、逆向工具名或私有数据来源，统一使用“查分器”、“曲目”、“谱面”、“成绩管理”等通用名词。

## 四、单条条目的详细程度（控制粒度与行动价值）

### 1. 核心判据：行动价值 vs 只是“知道一下”

> **这个细节，读者是要据此做什么，还是只是“知道一下”？**
>
> - **据此行动**（做判断、调整用法、改代码）——**写**。
> - **只是“知道一下”**（无决策价值的控件参数、构件名、常规技术行为）——**删**。

### 2. 必须砍掉的无行动价值细节（反面清单）

1. **构件名称与控件类型**：新增设置写清能力即可，不必点名控件类型（滑块、下拉框）或构件名（控制面板）。
2. **控件微调配置参数**：不写控件的取值范围（如 `-1 ~ 1`）、步长（如 `步长 0.1`）与默认值（如 `默认 0`）。
3. **伴随的技术实现行为**：不写「自动保存」「本地持久化」「实时生效」「写入 LocalStorage」等附带行为。

### 3. 必须保留的四类场景（正面清单）

以下四类场景具有强烈的行动决策价值或本身就是改动实质，必须准确写出：

1. **影响用户行为与使用边界的上限/配额**：例：`OAuth 应用现在最多可以登记 10 个回调地址`
2. **需要调用方据此分支处理的状态码**：例：`OAuth 授权时若 client_id 失效现在返回 404，客户端可据此重新注册`
3. **开发者向 API 字段与查询参数的默认值**：例：`获取曲目列表时 version 查询参数默认为 24000`
4. **交互形态或布局方式本身就是改动实质**：例：`排序与筛选整合至列表顶部工具栏，排序改为下拉菜单`、`移动端筛选改为底部抽屉`

### 4. 对比范例（改前 vs 改后）

- ❌ **改前（过度详细）**：控制面板新增「星星延迟」滑块，支持在 -1 ~ 1 范围调整延迟（步长 0.1，默认 0）并自动保存设置
- ✔ **改后（精炼得当）**：新增「星星延迟」设置，并改进滑条星星的淡入与出现时机

## 五、前后端统一更新日志处理规范

### 1. 统一发布载体与避免割裂

- 本项目更新日志统一维护在前端仓库的 `public/docs/changelog.md`。
- 同级 Go 后端服务仓库没有独立更新日志，**后端所有对外改动均直接汇总写入本文件**。
- **严禁打标签**：严禁给条目打 `[前端]`、`[后端]`、`[API]` 标签或设前后端专属小标题。
- **按业务功能整合**：前后端协同改动按业务功能整合为统一描述。

### 2. 后端/API 变动转译指南

后端提交需按业务效果与接口契约转译为人类语言：

1. **数据同步与业务逻辑**：`fix(score): ignore a client-supplied play_time` ➔ ``上传成绩时不再接受客户端提供的 `play_time`，该字段仅通过上传接口解析写入``
2. **API 结构体字段增删**：`feat(scores): add last_played_time` ➔ ``Score 结构体中新增 `last_played_time` 字段，用于获取谱面的最后游玩时间``
3. **协议与安全配额**：`feat(oauth): cap dynamic client registrations to 10` ➔ `OAuth 应用现在最多可以登记 10 个回调地址`
4. **错误码与响应格式**：`fix(oauth): answer an unknown client_id with 404` ➔ `OAuth 授权时使用已失效的 client_id 现在返回 404，客户端可据此重新注册`

### 3. 破坏性变动处理（Breaking Changes）

破坏既有契约（如删除 API、移除字段）时，在当日普通条目下方建立 `### ⚠ 破坏性变动` 区块：

```markdown
### ⚠ 破坏性变动

以下变动将会影响开发者，请检查你的代码是否受到影响：

- [结构体名] 结构体中删除字段：`旧字段名`
  > [替代接口名](/docs/api/...)请使用 `新字段名` 替代
```

## 六、排版结构与 Git 操作规范

### 1. 全局排版结构与格式约定

- 文件顶部固定为 `# 更新日志` 接分隔线 `---`。
- **日期标题规范**：二级标题 `## YYYY/M/D`，**严禁月份与日期前导补零**（必须 `2026/8/6`，严禁 `2026/08/06`）；**倒序排列**，最新日期紧接在 `---` 之后。
- **条目层级缩进**：独立条目使用一级列表 `-`；复合条目首行以冒号结尾，子条目缩进 2 个空格。
- **容器与引用块**：用户提醒可用 VitePress 容器 `::: info 提示`；迁移指引使用引用块 `> 提示文本`。

### 2. Git 操作与版本控制规则

- 更新日志路径为 `public/docs/changelog.md`，处于 git 正常追踪状态。
- 普通 `git add public/docs/changelog.md` 即可，**不需要也不得使用 `git add -f`**。
- 仓库根目录 `.gitignore` 中的 `/docs/` 仅针对根目录的 `docs/`，与 `public/docs/` 完全无关。
- 查阅历史仅使用只读 git 命令（如 `git log --oneline`、`git status`、`git diff`）。

## 七、从 Commit/PR 到更新日志的完整工作流程

```
步骤 1：查阅改动 ──► 检查前端仓库与同级 Go 后端仓库自上次发版以来的提交与合并 PR
        │
步骤 2：机械过滤 ──► 对照「排除清单」，剔除内部重构、CI、依赖升级、测试、无感知优化与回滚对消
        │
步骤 3：主动合并 ──► 按功能区域与问题面归并（参考单日 2~6 条，严禁无关凑数），未发布修复直接折叠进原条目
        │
步骤 4：读者分层 ──► 区分玩家向（通俗、禁用实现术语）与 API 向（精确契约术语），应用标准句式
        │
步骤 5：收紧粒度 ──► 依「行动价值」剔除控件类型、取值范围/步长与自动保存等实现行为，仅保留能力与行动数值
        │
步骤 6：规范插入 ──► 在 public/docs/changelog.md 顶部按 ## YYYY/M/D 格式排版插入
```

## 九、更新日志审查核对单

在提交或更新 `public/docs/changelog.md` 前，逐项对照以下清单审查：

- [ ] **条目判定（排除内部细节）**：对照机械排除清单，已剔除纯重构、无外部感知性能微调、CI/工程脚本、自动化测试、常规依赖升级及发版周期内的回滚对消。
- [ ] **未发布修复合并**：当前批次未发布代码的缺陷修补与打磨已全部消化、折叠进原条目，严禁单列为独立修复。
- [ ] **密度合理与严禁硬缝**：单日条目数以 2~6 条为参考基准（非硬性上限）；按功能区域与问题面归并；严禁为了凑数使用「并/以及」将无关变动强行缝合。
- [ ] **读者分层与用词边界**：玩家向条目通俗易懂，严禁泄漏水合、离屏合成、断点、派生数据等技术实现词；API 条目精准使用结构体与字段名；起始动词与句式遵循规范（「现在……」「修复……的问题」）。
- [ ] **详细程度（行动价值判据）**：根据“读者是要据此行动还是只是知道一下”收紧细节；新增设置仅写清“多了什么能力”，不点名构件名与控件类型，不罗列取值范围、步长与默认值；不写自动保存、本地持久化等常规实现行为；保留具有行动决策价值的配额上限、状态码、API 默认值与交互形态实质改动。
- [ ] **排版格式与破坏性变动**：日期严格遵循 `## YYYY/M/D`（无前导零、倒序排列）；字段名等标识符使用行内反引号包裹；破坏性变动必须单列 `### ⚠ 破坏性变动` 小节。
